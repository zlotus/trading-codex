# Project Context

## Purpose

Trading Codex is a personal A-share decision workspace for one operator. It
turns point-in-time historical data and opening-session snapshots into auditable
trade proposals, then mirrors manually entered fills into a local portfolio.

## Primary Workflows

1. Synchronize and validate historical and opening-session market data.
2. Research strategies with leak-resistant walk-forward backtests.
3. Produce a deterministic base target, optionally review a bounded AI
   allocation proposal, and apply hard risk controls.
4. Present actionable signals with prices, expiry, evidence, and risk flags.
5. Record actual fills and compare baseline, AI-adjusted, and actual portfolios.
6. Replay any decision from its exact data, strategy, configuration, and model
   versions.

## Goals

- Make every signal reproducible and attributable.
- Model A-share trading constraints and costs before evaluating performance.
- Adapt among pre-approved strategies as market conditions change.
- Keep AI useful for research, review, and bounded allocation without granting
  it authority over risk controls or fills.
- Provide a dense, quiet decision interface suited to repeated daily use.

## Non-Goals

- Automatic broker execution in the initial product.
- Sub-minute or high-frequency trading.
- Multi-user, commercial, or high-concurrency operation.
- Treating free market-data endpoints as permanent contracts.
- Deploying a strategy generated by AI on the same day it is created.

## Architecture

The system is a local modular monolith with two long-running processes: a
FastAPI API/worker boundary and a React web client. Market data uses immutable
raw artifacts and normalized Parquet datasets; DuckDB remains the planned query
layer, and transactional state is planned for SQLite.

The shared decision pipeline is framework-independent:

```text
point-in-time data -> features -> regime -> strategy intents -> allocation
  -> optional AI proposal -> deterministic risk -> execution plan -> ledger
```

RQAlpha is the selected replaceable execution-backtest adapter, isolated from
strategy code and the main application runtime. Qlib is reserved for later
factor and machine-learning research.

## Long-Term Constraints

- Runtime target is an ARM64 host in the Asia/Shanghai timezone.
- Historical and live decisions must use the same domain pipeline.
- Decisions must fail closed when required data is stale or inconsistent.
- The fill ledger is append-only; corrections use compensating events.
- User-entered fills are the source of truth for the actual mirrored portfolio.
- Secrets, raw market data, and generated experiment artifacts are not committed.

## Terminology

- **Base portfolio**: simulated portfolio driven only by deterministic strategy
  and risk logic.
- **AI portfolio**: simulated portfolio including approved AI allocation deltas.
- **Actual portfolio**: mirror derived only from manually recorded fills.
- **Decision run**: immutable record of the inputs and outputs for one decision
  checkpoint.
- **Point-in-time view**: data interface that rejects information newer than its
  declared `as_of` timestamp.
